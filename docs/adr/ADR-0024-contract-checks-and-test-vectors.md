# ADR-0024: Contract checks and test vectors as the module acceptance gate

- Status: Proposed
- Date: 2026-11-10
- Supersedes: none
- Superseded by: none

## Context

Independent module teams ship their own versions. This repository needs an automated, repeatable way to decide whether a module honors the ABI, its manifest and its capabilities, with failures that name the component at fault.

## Decision

- `praenora modules check <manifest> [--vectors F]` runs contract checks with stable ids and a pass, fail or skip result and message each: `manifest.schema`, `manifest.semantics`, `library.digest`, `library.load`, `library.entry_point`, `api.header`, `api.required_functions`, `describe.schema`, `describe.identity`, `lifecycle.create_destroy`, `lifecycle.full`, `invoke.result_schema`, `invoke.expected_outputs`, `invoke.determinism`, `invoke.malformed_input`, `self_test` (if present) and `unload`.
- The result is a `module-check-report` document plus a readable summary; exit code 0 only if no check failed.
- Test vectors (`kind: module-test-vectors`) hold cases with `capability`, `parameters`, `seed`, `time` and ticks; each tick gives `inputs` as `data` payloads (the tool builds envelopes) and optional `expect` with `outputs` and a `tolerance` (`relative` and `absolute`).
- A module version should pass its own test suite and the contract checks before this repository adopts it. Module teams can also use the in-process test kit (`include/praenora/sdk/testing.hpp`: a fake host that captures logs, controls cancellation and registers fake services).
- Contract checks are also run against fixture modules that break the contract on purpose.

### Builder notes (Proposed)

- The test kit's `FakeHost` enables every log level and records messages under a mutex, so modules may log from their own threads. It serves services registered by name and major version, can report a smaller `struct_size` to act as an older host, and, while `refuse_sink_writes(true)` is on, refuses the sink writes of calls made with it with `PRAENORA_STATUS_RESOURCE_EXHAUSTED`.
- `DirectModule` applies the host's table acceptance rules in its constructor and throws `std::invalid_argument` naming the broken rule. Calls without a created instance return `INVALID_STATE`, and `diagnostics()` returns `UNSUPPORTED` when the module lacks it; errors raised by the test kit itself are error documents. The module's `destroy` is called at most once, by `destroy()` or by the destructor.
- `DirectModule` takes any `praenora_module_get_api_fn`, including one looked up with `dlsym` in a built module, so the same driver works with linked and loaded modules.
- The fixture modules declare the test capability `test.echo@0.1.0`. The C fixtures share minimal implementations of the v0 functions (`tests/fixtures/modules/common/`), so each one breaks exactly one rule in its own table.
- Each example module ships `vectors.json` (`examples/modules/<module>/`): one case of two ticks, with the parameters, seed and time base of the example workflow. Its inputs and expected outputs are the data of the envelopes that module received and produced in the first two ticks of a run of the example workflow (from its message trace), checked first against the invariants of the example (the estimate of tick 0 rests on observations only, tick 1 blends, every value is finite and positive); the tolerance is `relative` 1e-9 and `absolute` 1e-12. `praenora_add_module(... TEST_VECTORS vectors.json)` copies the file beside the manifest, whose `tests.vectors` names it.
- Tests compare JSON with a tolerance through `json_near()` (`tests/support/json_compare.hpp`): two numbers match when `|a - b| <= max(absolute, relative * max(|a|, |b|))`, so zero tolerances ask for equality; objects need the same keys and arrays the same length; everything else must be equal. The contract checks compare outputs with vectors by the same rule, and by the same code: the rule has one implementation, header-only and using only the standard library and nlohmann/json (`src/runtime/core/json_near.hpp`); the runtime includes it, and the tests' `json_near()` forwards to it (through an include directory private to `praenora_test_support`, so the black-box tests still link only the shared library and see no internal header).
- The checks run in `detail::check_module()` (`src/runtime/api/module_check.hpp`), behind `Runtime::check_module()`; reading the test vectors and building a case's documents are in `src/runtime/api/module_check_cases.hpp`. Every id is reported, in the order above, and each check runs only when the one before it in its chain passed; otherwise it is skipped, saying "skipped because <id> failed" or repeating the reason of a skipped one. The chain runs from `manifest.schema` through `describe.identity` to `lifecycle.create_destroy` and `lifecycle.full`; `invoke.result_schema` and `invoke.malformed_input` follow `lifecycle.full`; `invoke.expected_outputs` and `invoke.determinism` follow `invoke.result_schema`; `self_test` and `unload` follow `describe.identity`. Problems of the module, its manifest or its vectors are failed checks, not exceptions; only a manifest file that cannot be read (missing, for example) is an `IO_ERROR` that `check_module()` throws, and so is a vectors file that cannot be read, once the manifest checks have passed (the vectors are read right after them, and not at all when they fail); both are thrown before any of the module's code runs, since nothing about the module can be learned from them.
- `manifest.schema` reads the file and checks its kind, `format_version` and the module-manifest schema. `manifest.semantics` covers what the schema cannot: `load_manifest()` (relative paths, unique capabilities, a compiling `parameters_schema`), compatibility with this runtime (`check_module_compat()`: platform, ABI major, PMP version) and that the catalog defines each capability and the message types of its ports.
- `library.digest`, `library.load`, `library.entry_point`, `api.header`, `api.required_functions`, `describe.schema` and `describe.identity` are the nine steps of `LoadedModule::load()`, grouped: an overload, `load(manifest, Check* reached)` (interface addition), says which step it was taking when it threw, and that check fails with the loader's message.
- The instances belong to a step named `check`, with the deadlines invoke 30 s (also for `self_test`), lifecycle 10 s and a cancellation grace of 5 s, the runtime services of the runtime context, and the runtime's logger `module.check` for module log messages. After a call that never returned, the checks that would call into the module again are skipped, and `unload` fails, since the library has to stay loaded.
- The lifecycle checks and `invoke.malformed_input` use the first case of the vectors, or without usable vectors the manifest's first capability with the `parameters_schema`'s defaults (seed 0, time base unit "1", start 0, period 1); when the defaults do not satisfy the schema, they are skipped with that reason. A module whose parameters have no usable defaults and that ships no test vectors therefore passes with its lifecycle and invocation checks skipped, each saying why: the checks cannot make parameters up, so such a module should ship vectors. `lifecycle.create_destroy` creates and destroys an instance; `lifecycle.full` creates, initializes, finalizes and destroys one, without invoking it (the invocation checks run whole lifecycles of their own).
- Vectors come from `--vectors` (`vectors_path`), else the manifest's `tests.vectors`. They are read as a `module-test-vectors` document with its schema's defaults, and checked before anything runs: each case's capability is one the manifest lists, its parameters satisfy the `parameters_schema` (whose defaults are then applied), each tick's inputs and expected outputs name ports of the capability, every required input is present, and every datum satisfies its port's message type. The vectors are read only once the manifest checks have passed (when they fail, they are never opened). Invalid vectors then fail `invoke.result_schema`, located in the file, whatever the loading and lifecycle checks did (also when no instance could be created), and the two checks after it are skipped.
- A case's documents are the engine's: create with the step `check`, the case's capability, the module and the parameters; initialize with the case's seed (as given, not derived from a step id), the case's time base and a run fingerprint, the SHA-256 of the case's canonical JSON; for tick t an invocation with `logical_time` the end of window t, each input's data in an envelope of its port's message type, with source `inputs.<port>`, tick t and that logical time.
- `invoke.result_schema` applies the engine's acceptance rules to each result: JSON, `pmp-result`, only declared output ports, every required one, each datum valid for its message type. Both use the same function, `check_invoke_result()` (`src/runtime/engine/result_check.hpp`), so the checks accept exactly the results a run accepts. `invoke.expected_outputs` compares the `{port: data}` of a result with `expect.outputs` through `json_near()` (`src/runtime/core/json_near.hpp`, the rule above), so the ports must be the same; a tolerance defaults to 0 for both bounds; without any `expect` it is skipped. `invoke.determinism` runs every case a second time on a new instance and compares the result bytes tick by tick, reporting the first differing byte with an excerpt of both results. `invoke.malformed_input` passes when `invoke("{")` returns an error status in time; OK, a timeout or a call that never returns fail.
- `self_test` calls the table's `self_test` through `ModuleInstance::self_test()` (interface addition: in state loaded, before create, with the invoke deadline) and passes when the report is `{"passed": true, ...}`, listing the failed sub-checks otherwise; without the function it is skipped, unless the manifest declares `features.self_test`, which then fails.
- `unload` releases the last reference to the library (dlclose or FreeLibrary) once every instance is destroyed. Whether the operating system then unmaps the image cannot be observed portably (glibc keeps libraries with unique symbols loaded, macOS images with thread-local variables), so the check passes when the release returns; it is skipped when `PRAENORA_DEBUG_KEEP_LIBRARIES=1` pins every library.
- The fixture `fx-nondeterministic` answers with a counter shared by its instances and ships `vectors.json` (`praenora_add_fixture_module(... TEST_VECTORS ...)`), so `invoke.determinism` fails, `invoke.expected_outputs` (its vectors expect no outputs) and `self_test` (it has none) are skipped, and the other checks pass (`unload` is skipped where `PRAENORA_DEBUG_KEEP_LIBRARIES=1` keeps libraries loaded).
- `praenora modules check` prints one line per check and a count; when a check failed, the command fails with `FAILED` (exit code 1), the report in the error's details.
- CTest labels name kinds of tests, not components: `unit`, `protocol`, `contract`, `negative`, `lifecycle`, `integration`, `cli`, `python`, `install`, `perf` and `docs`. There is no label per component (no `sdk`, `document`, `catalog`, `config`, `discovery`, `compat`, `loader`, `instance`, `graph`, `engine`, `io`, `observability` or `api` label). A component's tests are selected by their GoogleTest suite name instead, which names the component (`ctest -R '^Loader\.'`); [docs/testing.md](../testing.md#labels) lists the suites of each label.

## Alternatives considered

- **Module tests only.** Cannot check host-side expectations uniformly.
- **Manual review at adoption.** Slow and inconsistent.
- **Checks at load time on every run.** Costs run time; the same checks remain available through `validate --load`.

## Consequences

- A shared, documented bar for new module versions.
- Vectors are also useful as regression tests for module teams.
- The check list is part of the contract and changes need a new minor version.
