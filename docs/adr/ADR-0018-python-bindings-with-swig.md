# ADR-0018: Python bindings with SWIG over a narrow facade; scikit-build-core; namespace package

- Status: Proposed
- Date: 2026-11-10
- Supersedes: none
- Superseded by: none

## Context

Python users need the same features as the CLI. Binding the C++ API directly would expose internals and tie Python to C++ ABI details.

## Decision

- SWIG 4.x generates the bindings. The `.i` interface wraps only a narrow facade, `praenora::python::...`, whose inputs and outputs are strings, integers and floats; JSON travels as strings. Nothing else is `%include`d.
- A hand-written pure-Python layer (`praenora.runtime`) provides the public API with CLI parity: `version`, `validate`, `validate_document`, `list_modules`, `inspect_module`, `check_module`, `graph`, catalog and schema queries, `read_status`, and a `Workflow` context manager.
- C++ `praenora::Error` becomes a Python exception carrying a JSON payload, re-raised as `praenora.runtime.PraenoraError` with `code`, `name`, `category`, `message` and `details`.
- Long calls release the GIL, so another thread can call `status()` or `request_stop()` during a run. Python interrupt behavior during a blocking `run()` is open (OQ-25).
- `praenora` is an implicit namespace package (no `praenora/__init__.py`). The wheel is built from the root `pyproject.toml` with scikit-build-core and contains the package, the extension and the shared library, with RPATH `$ORIGIN` or `@loader_path` (the DLL beside the extension on Windows).
- Requires Python 3.10 or newer with a version-specific extension (OQ-21). Tests use stdlib `unittest`.

### Builder notes (Proposed)

- Document limits apply to input handed through the facade: document files up to 16 MiB, JSON and YAML nesting depth up to 128, and module results up to 256 MiB by default. Facade calls surface document-size and nesting limits as `PARSE_ERROR` (raised to Python as `PraenoraError` with name `PARSE_ERROR`).
- `swig_add_library()` (UseSWIG) builds the extension from `src/python/praenora_runtime.i`, which wraps only `src/python/facade.hpp` (namespace `praenora::python`), with SWIG `-threads`. Only the facade's wrappers release the GIL: the interface puts SWIG's own string and string-vector code (`StringVector`, its iterators and slices, which call the Python C API, and its destructor) under `%nothreadallow`, so a slice index too large for C or an iterator's value is handled while the GIL is held. A test runs those helpers in a fresh `python -X dev`, which aborts when memory is allocated without the GIL. The build tree holds the importable package in `<build>/python/praenora/runtime`: the native module `_bindings_native` with the interpreter's extension suffix (from `Python3_SOABI`, for example `_bindings_native.cpython-312-darwin.so`, so only that interpreter loads it), SWIG's proxy module `_bindings.py` (`%module(package="praenora.runtime") _bindings`) and `__init__.py`, which the build copies from `python/praenora/runtime/`. The native module cannot have SWIG's default name `__bindings`: the proxy names its native module inside class bodies, where Python mangles names that begin with two underscores; nor `_bindings`, the proxy's own name. The extension exports only its module init function. On multi-configuration generators every configuration builds into the same package directory (not yet verified).
- Errors. The facade throws a `praenora::Error`, and any other `std::exception` except `std::bad_alloc` as `INTERNAL` ("internal error: <what>", as the CLI reports it), as `std::runtime_error("PRAENORA_ERROR_JSON:" + Error::to_json())`; an argument mistake is `INVALID_ARGUMENT`, the code of the CLI's usage errors. The `%exception` handler maps `std::bad_alloc` to `MemoryError` and every other exception to `RuntimeError` with its message. `-threads` releases the GIL only inside `$action`, whose scope ends, taking the GIL back, before a handler runs, and each handler also takes the GIL explicitly (`SWIG_PYTHON_THREAD_BEGIN_BLOCK`) before it sets the Python error. The package re-raises a `RuntimeError` that carries the prefix as `PraenoraError` (`code`, `name`, `category`, `message`, `details`, `location`), without the `RuntimeError` as its context; `str()` gives "NAME: message", the error survives pickling, and details that are not a JSON object would be kept as `{"text": ...}`.
- `validate()` and `validate_document()` return the report when it holds no error, warnings and notes included; otherwise they raise as `praenora validate` fails: the first error's code and location, the message "<file>: validation failed: N error(s)" and the report in `details`. `check_module()` returns the check report when no check failed and otherwise raises `FAILED` ("N of M contract checks failed: <ids>", the report in `details`), as `praenora modules check` fails. `Workflow(...)` raises what `Runtime::open()` throws; `run()` returns for a completed or stopped run and raises the failure of a failed one.
- Results have the keys of the CLI's `--json` results: module entries `{"name", "version", "manifest_path", "library_path", "os", "arch", "capabilities"}`, with `"describe"` and `"library_sha256"` when loaded; catalog entries `{"kind", "id", "version", "status", "summary"}`; the run summary `{"state", "ticks_completed", "fingerprint"}`, without the output directory (neither the facade nor `Workflow` exposes `Workflow::output_dir()`). `tick()` returns `{"tick", "logical_time", "outputs", "finished"}`; the `state` and `fingerprint` properties are plain strings; `run_record()` is `None` before the run starts. `graph()` returns a dict for `format="json"` and a string for the other formats, AsyncAPI included. `list_catalog(kind)` takes the CLI's `--kind` values (`workflows`, `capabilities`, `messages`). These documents and failures, and the names that both front ends take (catalog kinds, graph formats, log levels and formats, the limit of seeds and tick counts), come from `praenora::frontend` (`src/frontend/`, ADR-0023), which the CLI uses too, so the two cannot drift apart; the facade itself shapes only what the CLI has no equivalent for (`tick()`'s result) and checks the options document.
- Signatures: `validate(config, module_paths=None, catalog_paths=None, load=False)`, `list_modules(module_paths=None)` and `inspect_module(name, version=None, load=False, module_paths=None)`; `graph(config=None, workflow=None, format="json")`, `list_catalog(kind=None)`, `catalog_entry(id, version)` and `check_module(manifest, vectors=None)` take `module_paths` and `catalog_paths` (as far as they use them) as keyword-only arguments; `Workflow(config, module_paths=None, output_dir=None, seed=None, log_level=None, *, ticks=None, overwrite=False, trace_messages=None, status_file=None, log_format=None, log_file=None, catalog_paths=None)`. Search paths that are `None` are an empty list, so the runtime's usual search order applies, environment included (the facade always sets `use_environment`).
- Arguments. Paths are `str` or `os.PathLike` (`os.fspath()`; a bytes path is a `TypeError`), and one path where a list of paths is expected is a `TypeError` (SWIG would split a string into its characters). The flags `load`, `overwrite` and `trace_messages` go through `bool()`. Only the `Workflow` arguments that are not `None` go into the facade's options document (integers of other types, such as numpy's, through `operator.index`). The facade refuses an unknown key and a bad value with `INVALID_ARGUMENT`: `seed` and `ticks` are whole numbers from 0 to 2^53 - 1, as for `--seed` and `--ticks`; `log_level` and `log_format` take the names of `--log-level` and `--log-format`, in any case; `null` stands for a key not given. `run(ticks)` takes `None` (until the run is finished) or such a number; anything else, a bool or a negative number for example, is `INVALID_ARGUMENT` too, checked in Python, so the facade's `-1` ("until finished") is never passed as a count.
- A workflow's logging arguments are also the logging of the `Runtime` that opens it (`RuntimeOptions::logging`), as the CLI's `--log-*` flags are. Unlike the tool, the facade does not write them into the process environment (a library must not), so `PRAENORA_LOG_LEVEL` and `PRAENORA_LOG_FORMAT` still win for the runtime's own few records (such as "runtime ready"), while the arguments win for the run's.
- Each facade call constructs its own `Runtime`, which reads the catalog and indexes the module search paths anew, as each CLI command does; a `WorkflowHandle` keeps only its `Workflow`, which holds the runtime context it needs.
- Tests. CTest test `python.unittest` (label `python`, timeout 300 s) runs `python -m unittest discover -s tests/python -v` with the interpreter that `find_package(Python3)` found, and the environment `PYTHONPATH=<build>/python`, `PYTHONDONTWRITEBYTECODE=1` (nothing is written into the source tree), `PRAENORA_TEST_MODULES_DIR`, `PRAENORA_TEST_PROVIDERS_DIR`, `PRAENORA_TEST_CATALOG_DIR`, `PRAENORA_EXAMPLE_CONFIG` and, when the examples are built, `PRAENORA_EXAMPLE_MODULES_DIR` (otherwise the tests that need the example modules are skipped). It sets `PRAENORA_LOG_LEVEL=off`, so the test output holds only the tests' own lines (explicit per-run levels still win), and unsets `PRAENORA_MODULE_PATH`, `PRAENORA_PROVIDER_PATH`, `PRAENORA_CATALOG_PATH` and `PRAENORA_LOG_FORMAT`, so the caller's environment cannot change the results; tests that exercise the environment set it themselves. `tests/python/support.py` holds what the test modules share: the environment, the fixture paths and `captured_stderr()`, which sends file descriptor 2 to a temporary file. The tests of the example workflow use it: the example configuration sets its predict step's `log_level` to debug, which outranks the run's level (ADR-0015), and Python has no way to detach the runtime's standard-error sink (`RuntimeOptions::logging.to_stderr` is not exposed). The tests write only to temporary directories, including the configurations of the test workflows that they write, as the C++ integration tests do. Two tests show that the calls release the GIL: a second thread polls `status()` during `run()` and sees the run running, and a second thread calls `request_stop()` while `run()` is in progress; both fail when the extension is built without `-threads`.
- With `PRAENORA_SANITIZERS` set, the extension still builds, but `python.unittest` is registered `DISABLED`: the instrumented extension and runtime library cannot be loaded into an interpreter that is not instrumented itself unless the sanitizer runtime is preloaded (`DYLD_INSERT_LIBRARIES`, `LD_PRELOAD`), and the interpreter's own allocations would then be checked too. The C++ tests of the API keep running under the sanitizers.
- Windows (not yet verified): the extension's suffix is `.pyd`; `praenora_runtime.dll` and the third-party DLLs are copied beside it (`$<TARGET_RUNTIME_DLLS>`), where Python looks for the libraries of an extension; `SWIG_PYTHON_INTERPRETER_NO_DEBUG` lets Debug builds use the release Python library.
- Wheel. Built and verified on macOS arm64 (macOS 15, CPython 3.12, scikit-build-core 1.1.2, Homebrew's SWIG 4.5.1) offline, with scikit-build-core installed beforehand and `--no-build-isolation`; a build that downloads its requirements is not yet verified. The wheel holds only `praenora/runtime/` and its `.dist-info`: `__init__.py`, `_bindings.py`, the extension and the runtime library, 0.84 MB (2.0 MB installed), and it imports and passes the tests of `tests/python` in a fresh virtual environment. With `SKBUILD` defined, the install rules put the extension, `_bindings.py` and the runtime library (without its development symlink and import library) into `praenora/runtime/`; `__init__.py` comes from `pyproject.toml`'s `wheel.packages` only. scikit-build-core leaves out a package file that an install rule has already installed, so the earlier rules, which installed `__init__.py` too, did not collide; the install rule's copy won without a warning. A wheel cannot hold a symbolic link: the first wheel stored the soname link `libpraenora_runtime.0.1.dylib` as a second copy of the library (1.55 MB instead of 0.84 MB, built the same way). In a wheel build the runtime library's `VERSION` is therefore its `SOVERSION`, so its only file is named by its soname (`libpraenora_runtime.0.1.dylib`; `libpraenora_runtime.so.0.1` on Linux, not yet verified), and `MACHO_CURRENT_VERSION` keeps the full runtime version. The extension's only RPATH is `@loader_path` on macOS (`$ORIGIN` on Linux; on Windows the DLL lands beside it), and the runtime's install name is `@rpath/libpraenora_runtime.0.1.dylib`. The runtime library's own third-party shared libraries are not bundled (OQ-13): the macOS wheel links Homebrew's yaml-cpp, spdlog and fmt by their absolute paths. `pyproject.toml` takes the version from `project(VERSION)` in `CMakeLists.txt` through `tool.scikit-build.metadata`, which scikit-build-core 1.1.2 deprecates in favor of `[[tool.dynamic-metadata]]` and warns about unless the minimum version is below 1.0; `minimum-version = "0.10"`, the oldest version `build-system.requires` accepts, keeps that table working without a warning, and keeps 0.10's defaults under newer versions, among them metadata written as `Metadata-Version: 2.1` instead of 2.2 (the same fields). The macOS platform tag comes from a `CMAKE_OSX_DEPLOYMENT_TARGET` define, else `MACOSX_DEPLOYMENT_TARGET`, else the running macOS version, never from the project's default of 11.0, which CMake keeps even when `MACOSX_DEPLOYMENT_TARGET` is set; [docs/python.md](../python.md#building-a-wheel) says to give the define. With `MACOSX_DEPLOYMENT_TARGET` alone, the tag names the variable's version (checked with 15.0) while the binaries target 11.0.
- The package's install rules (`cmake/PraenoraInstall.cmake` and the `install()` rules of `src/runtime`, `src/sdk`, `src/cli` and `examples`) exist only when `PRAENORA_INSTALL_RULES` is ON (`cmake/PraenoraOptions.cmake`): `PRAENORA_INSTALL` is ON and `SKBUILD` is not set. scikit-build-core packs every install rule into the wheel, so a wheel build has only the Python package's own rules, and the wheel holds just `praenora/runtime/` (no headers, CMake package or `share/praenora`). Configured with `-DSKBUILD=2` and the defines of `pyproject.toml`, the build generates exactly the three install rules of `src/python`, all into `praenora/runtime`. Conversely, a normal installation holds nothing of the Python package; the install test checks that no `*.py` or `*_bindings*` file is installed.
- Service providers ([ADR-0026](ADR-0026-runtime-service-providers.md)): `list_providers(provider_paths=None)` returns the array of `praenora providers list --json`; `validate()`, `check_module()` and `Workflow` take a keyword-only `provider_paths`, which the facade passes on as `RuntimeOptions::provider_paths` (`WorkflowHandle` as the option `provider_paths`). `inspect_module()` takes none: inspecting a module loads no provider.

## Alternatives considered

- **nanobind or pybind11.** Pleasant C++ ergonomics, but target Python only and bind C++ types, which the project wants to avoid. SWIG makes other languages cheap later.
- **ctypes or cffi over a C API.** No build-time dependency, but needs a separate C API layer the MVP does not have.
- **Cython.** Another language and toolchain for little gain.
- **CLI subprocess wrapper only.** Cannot query status of a live run.

## Consequences

- The facade limits what Python can reach, matching the anti-goal against exposing internals.
- Maintaining the `.i` file and the wrapper adds work for every new feature.
- The wheel build needs SWIG and scikit-build-core; it is verified with both installed beforehand (`--no-build-isolation`), not yet with requirements that the build downloads.
