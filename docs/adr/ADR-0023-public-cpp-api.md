# ADR-0023: Public C++ API: exceptions, pimpl, no third-party types in public headers

- Status: Proposed
- Date: 2026-11-10
- Supersedes: none
- Superseded by: none

## Context

The C++ API is shared by the CLI, the Python bindings and embedding applications. It should not force their build to match ours, nor expose dependency types that would make those dependencies public.

## Decision

- Public headers use only the standard library and Praenora types; no nlohmann, spdlog or yaml-cpp types appear, so all third-party dependencies link PRIVATE. Public classes use the pimpl pattern. Exports use a generated `PRAENORA_RUNTIME_API` macro with hidden visibility by default.
- Errors are exceptions: `praenora::Error` carries code, name, category, message, details and location. Validation returns a `ValidationReport` of all diagnostics instead of throwing on the first.
- `Runtime` is immutable and thread-safe. `Workflow` is one non-copyable run: control methods (`start`, `tick`, `run`, `close`) must not run concurrently with each other (misuse fails with `INVALID_STATE`); status queries and `request_stop` are safe from any thread. `close()` is idempotent and also runs from the destructor; destructors never throw.
- The C++ API is source-compatible under SemVer but not ABI-stable across compilers. The only binary-stable interface is the module C ABI.
- All internals compile into one OBJECT library linked into the shared runtime and into white-box tests.
- Paths are UTF-8 strings.

### Builder notes (Proposed)

- The `praenora` CLI is a thin layer over this API. `praenora help`, `-h` and `--help` print usage to stdout and exit 0. No command, an unknown command or an unknown option prints usage to stderr and exits 2. `praenora version --json` prints `{"ok":true,"result":<version_info_json()>}`.
- The shared library exports only symbols of the `praenora` namespace, with the type information and vtables of its classes. The runtime's own code is compiled with hidden visibility, and the symbols of statically linked dependencies (such as json-schema-validator) are kept internal at link time: an exported-symbol pattern list on macOS (verified), and on other ELF platforms a version script (an `extern "C++"` pattern for `praenora::*`, and the mangled-name patterns `_ZTIN8praenora*`, `_ZTSN8praenora*` and `_ZTVN8praenora*` for its type information and vtables, since a version script matches a quoted demangled name such as `"typeinfo for praenora::Error"` literally, never as a pattern; everything else local) plus `--exclude-libs,ALL` (built and tested under Docker, on Ubuntu 24.04 with GCC 13; not yet verified on GitHub). Windows exports only `dllexport` symbols anyway.
- `Runtime` (`include/praenora/runtime/runtime.hpp`) keeps one immutable state behind a `std::shared_ptr<const Impl>`: the runtime context (`make_runtime_context()`: catalog, module index, services), the environment's logging settings and the runtime's own log hub, all read once in the constructor. Copies share it; there are no move operations, so a "moved-from" Runtime is a copy and stays usable. A `Workflow` holds the context itself, so it may outlive the Runtime that opened it.
- `Runtime::open()` validates (with the `WorkflowOptions` as overrides), resolves the run's logging (ADR-0015), then refuses a log file (the run's, from any source, or the runtime's) at or under a path that the output directory manages, which an overwrite would remove while it is open (`CONFIG_INVALID`, located at `/observability/log_file` when the configuration names it; compared by resolved path and, where the paths exist, by file identity; ADR-0019), then builds the run so that nothing that can fail runs after an earlier run in the output directory is removed: `check_output_dir()` (an earlier run is refused without `overwrite`, and nothing in the directory changes), the run's own log hub (which may create its log file), the engine (which registers the run and its steps with the run's metrics), `prepare_output_dir()` with `overwrite` (which creates the directory or removes the earlier run's files) and, last, the status-file writer, whose first write is in its constructor, so a status file inside the directory is never written before an earlier run is refused, nor removed afterwards. The writer's producer is the metrics' snapshot and its error handler sets the run's last error; both use only the metrics, so the writer is declared before the engine and outlives it: whether or not `close()` ran, a state change that the engine's destructor makes still reaches the status file, and the writer's last write shows the final state. The engine's `on_state_change` notifies the writer through an atomic pointer that `close()` clears before it destroys the writer; `request_stop()` never notifies, so it stays lock-free and async-signal-safe. When validation reports an error, `open()` throws the first error's code and location with the message `workflow validation failed: N error(s)` (N errors, warnings not counted) and the report's JSON as details.
- Control calls (`start`, `tick`, `run`, `close`) take an atomic busy flag; one that finds it taken fails with `INVALID_STATE` ("... in progress") before touching anything. `close()` cannot fail: while another thread is in a control call it only requests a stop (the engine may not be shut down under a running call), and that call winds the run down; a later `close()` or the destructor finishes closing. Destroying a workflow while another thread still calls it is not allowed.
- `close()` ends a ready or running run as `stopped` (`Engine::shutdown()`), lets the status-file writer write once more and destroys it, and marks the workflow closed: every later control call is `INVALID_STATE`, also for a workflow that never started (whose engine would otherwise still be startable). The engine itself stays until the destructor, so queries keep working after `close()`, also concurrently with it.
- `run()` starts a workflow that has not started, then runs ticks while the engine is not finished (and fewer than `max_ticks` ran): a stop requested between ticks is wound down by the next tick, which calls no module, so the loop ends as `stopped` (ADR-0011). It returns normally only for a run that goes on, is completed or is stopped. The workflow keeps the error that `start()`, `tick()` or `run()` threw when the run failed, and `run()` on a failed run throws it again, with the same code, message, location and details. `start()` and `tick()` refuse a state that does not allow them (`start()` anything but `created`; `tick()` anything but `ready` and `running`) before they call the engine, so a refusal (`INVALID_STATE`) is never kept as the run's failure. A failed run always ends in a control call that throws (ADR-0011), so the error `run()` throws again is the kept one, except when that call threw something other than a `praenora::Error`: in practice `std::bad_alloc`, which the engine passes on unchanged once the run is over. Then `run()` falls back to the run's error record (code and message, without details), which a failed run always has.
- `validate(config, {load = true})` loads the library of each resolved manifest once (`LoadedModule::load()`: table, `describe()` identity), reports a failure for the first step, in schedule order, that uses the module (with the module's `name@version`), reports `LIBRARY_DIGEST_MISMATCH` when the library is no longer the file validation hashed, and releases the libraries before it returns.
- `validate_document()` takes a document's kind from its `kind` field (the kinds of the schema registry other than the module ABI's) and its schema version from `format_version`; a document without `kind` is a module-ABI document whose kind is the one `pmp-*` kind whose required fields it has (`DOCUMENT_KIND_MISMATCH` when none or several fit), with its schema version from `pmp_version` (the runtime's PMP version when absent, as `pmp-result` allows). Every schema problem is a `SCHEMA_VIOLATION` located in the document.
- `list_modules()` lists every indexed manifest in scan order, other platforms' included. `inspect_module()` without a version takes the module's highest version for this platform; when only other platforms have it, discovery's `PLATFORM_MISMATCH` explains why, and an unknown name is `MODULE_NOT_FOUND` naming the search paths.
- `read_status_file()` refuses a file whose `kind` is not `status-snapshot` (`DOCUMENT_KIND_MISMATCH`) and returns the file's text unchanged.
- `check_module()` runs the contract checks (ADR-0024); `ModuleCheckReport::passed()` and `to_json()` (`{"kind", "format_version", "passed", "checks"}`) give its outcome and its `module-check-report` document.
- `graph()` takes exactly one of `config_path` and `workflow` (`"<name>@<version>"`; `INVALID_ARGUMENT` otherwise or for a malformed one). Of a configuration only the workflow section matters: it is read with `read_workflow_config()`, and only an error that keeps the document from being read, or one under `/workflow`, is thrown, with the report in the details. An unknown definition is `WORKFLOW_NOT_FOUND`; an invalid one throws its first problem, with every problem (a validation report) in the details; the message is "invalid workflow definition: " followed by the problem's own message, which names the workflow ("workflow <name>@<version>: ..."), so the name is not repeated. The formats, each ending in a newline: `text` ("workflow:", "schedule:" and "connections:", one line per connection in definition order, "[delay 1]" after a delayed one), `json` (`{"workflow": {"name", "version"}, "schedule", "connections": [{"from", "to", "delay", "type", "type_version"}]}`), `dot` (left to right; boxes `inputs` and `outputs` when the definition declares any, the steps in schedule order, edges labeled "<from port> -> <to port>", delayed edges dashed) and `asyncapi` (ADR-0020).
- `list_catalog()` returns the catalog's entries in (kind, id, version) order. `catalog_entry()` returns an entry's canonical JSON; an id@version that entries of more than one kind share is `INVALID_ARGUMENT` naming the kinds, and an unknown one `CATALOG_ENTRY_NOT_FOUND` listing the id's versions. `list_schemas()` returns the sorted `"<kind>@<major>.<minor>"` of the embedded schemas; `schema()` returns an embedded schema's text, of the highest version when none is given, for a version written `major.minor` or as a whole semantic version (a malformed one is `INVALID_ARGUMENT`; an unknown kind or version `FORMAT_VERSION_UNSUPPORTED`, which names the kinds when the kind is unknown).
- Diagnostics about a catalog entry are located in it: `Catalog::locate(kind, id, version, pointer)` (interface addition) gives the entry's origin as the file (the file it was read from, or `catalog/<path>` for an embedded entry) with the line and column of the pointer. The graph's diagnostics (`validate_graph()`, also used by `graph()`) and validation's diagnostics about unknown message types and capabilities of a definition (and of a capability's ports) use it, so `validate` and `graph` locate them like the configuration's own.
- `Workflow::output_dir()` (interface addition) returns the run's output directory as an absolute UTF-8 path, empty when the run writes no files; `praenora run` prints it.
- The CLI's commands are `version`, `validate` (a configuration, or `--document`), `modules list|inspect|check`, `graph`, `run` (with `--overwrite` for an output directory that holds an earlier run), `status`, `catalog list|show` (`list --kind workflows|capabilities|messages`) and `schema list|show`, and `praenora help [<command>]` prints a usage. Every command accepts the global flags `--json`, `--module-path` and `--catalog-path` (repeatable), `--log-level`, `--log-format`, `--log-file` and `--help`/`-h` (its usage, on standard output, exit 0; with `--json`, the usage text is the `result` of the success document, so standard output still holds exactly one JSON document, as it does for `praenora help`). Flags may come before or after the arguments, values as `--flag V` or `--flag=V`, and `--` ends the flags; global flags may also precede the command. Arguments are UTF-8; on Windows the tool reads its wide arguments, sets the console's output code page to UTF-8 and writes standard output and error in binary mode, so lines end in "\n".
- With `--json`, standard output holds exactly one document, `{"ok":true,"result":...}` or `{"ok":false,"error":<Error::to_json()>,"diagnostics":[...]}`; human-readable messages and diagnostics go to standard error in both modes, diagnostics in the `ValidationReport::to_text()` format, and an error without a file starts with "praenora: ". JSON results hold the API's documents as values: a validation report, module info (with `describe` as an object when loaded), the check report, the catalog entry, the schema, the status snapshot, the graph for the JSON formats (a string for text and dot), and for `run` `{"state", "ticks_completed", "fingerprint", "output_dir"}`.
- Exit codes come from the first error's code; an error that carries a validation report (details `{"ok", "diagnostics"}`, as `open()` and `graph()` throw them) is a validation failure and exits with 3, as does `validate` when its report holds an error. A missing or unreadable configuration, document, manifest or status file exits with 74 from every command (a missing or unreadable data file is `TARGET_DATA_INVALID`, 3): a validation report whose errors are all `IO_ERROR` maps to 74 (any other error keeps 3), `status` and `modules check` throw `IO_ERROR` for a file they cannot read (`check_module()` does so for its manifest and its vectors file, before any module code runs). `modules check` with a failed check fails with `FAILED` (1), the report in the details. A stopped run prints its summary and fails with `RUN_STOPPED` (130), the summary in the details; a failed run prints its summary before the error.
- Later: [ADR-0031](ADR-0031-raise-the-reserved-error-codes.md) makes a missing or unreadable data file `TARGET_DATA_UNAVAILABLE`; it still exits with 3, as an error of a validation report.
- The logging flags take level and format names in any case; another value is a usage error (exit 2). The tool writes them, by their canonical names, into its own environment (`PRAENORA_LOG_LEVEL`, `PRAENORA_LOG_FORMAT`; `setenv` or `_putenv_s`) before it constructs the `Runtime` and before any thread starts, so they also win over the environment for the runtime's own logging without an API change; `--log-file` sets `RuntimeOptions::logging.file`. `run` passes all three as the `WorkflowOptions` overrides too. `--ticks` and `--seed` take integers from 0 to 2^53 - 1.
- `praenora run` stops on SIGINT and SIGTERM (Ctrl+C, Ctrl+Break and closing the console on Windows). On POSIX it keeps a disposition of `SIG_IGN` that it inherits at startup for either signal, as other tools do (a shell starts a command in the background with SIGINT ignored): it looks at the disposition first and installs its handler only for a signal that is not ignored. A `sigaction()` (or `SetConsoleCtrlHandler()`) handler sets a flag, a watcher thread that looks at it every 50 ms calls `request_stop()`, and a second signal ends the process at once with `_Exit(130)`. On Windows the system ends the process once the handler of a console close, logoff or shutdown event returns (or about 5 s after the event), so for these the handler requests the stop and then waits, at most 4 s, on an event that the tool sets once the watched run is over (its modules finalized and destroyed), before it returns. The flag is a lock-free `std::atomic<std::sig_atomic_t>`: a `volatile std::sig_atomic_t` may be set in a signal handler too, but reading it from another thread is a data race (ThreadSanitizer reports it), while a lock-free atomic is safe in both places. The CLI writes its JSON with nlohmann/json, which it links privately, like the runtime.
- The `cli` label holds two kinds of tests. The CLI driver tests (names `cli.<command>.<case>`) run the tool through `tests/cli/run_cli.cmake`, a CMake script that checks the exit code, regular expressions on both outputs, values at paths of the JSON document, a file's bytes and files left behind; it can remove a directory first (`CLEAN_DIR`), copy files into place (`COPY_FILES`, pairs of source and destination, their directories created), run a command before (which must succeed) and one after. The `CliTable.*` and `Frontend.*` tests (executable `praenora_cli_tests`) are unit tests of the tool's header-only helpers and of `praenora_frontend`, which it shares with the Python extension.
- MSVC: the exported `Runtime` and `Workflow` hold standard smart pointers, so their headers disable warning C4251 around the classes, as `error.hpp` does.
- `ValidationReport::error_count()` and `ValidationReport::first_error()` (interface addition): the number of diagnostics with severity error, and the first of them (`nullptr` when there is none; the pointer is valid until the diagnostics change). `Runtime::open()` builds its failure from them, and so do the front ends, instead of counting by hand; `Runtime::graph()` and the graph builder (`detail::build_graph()`) take the first problem of an invalid workflow definition from `first_error()` as well.
- The two front ends of the API, the `praenora` tool and the Python extension (ADR-0018), share one internal component, `praenora_frontend` (`src/frontend/frontend.hpp`, namespace `praenora::frontend`), so that what they report cannot drift apart: the JSON of a module (`module_json()`, with `describe` and `library_sha256` when loaded), of a catalog entry and of a run's summary (`{"state", "ticks_completed", "fingerprint"}`, to which the tool adds `output_dir`); the failure of a validation (`validation_failure()`: the first error's code and location, "<what>: validation failed: N error(s)", where an empty path is written `''`, as the diagnostics write it, so that the message never starts with ": ", and details that the caller chooses, none for the tool, the report for Python) and of the contract checks (`check_failure()`: `FAILED`, "N of M contract checks failed: <ids>", the report as details); the names that both take, each kind of name in one table of the names and the values they stand for (`kCatalogKinds`, the catalog kinds by the names `--kind` takes: workflows, capabilities, messages; `kGraphFormats`; `kLogLevels` and `kLogFormats`, the canonical names, parsed in any case), from which the lookups, the lists of names that error messages give (`names_of()`: "a, b or c") and the lists in the tool's usage texts ("a, b or c", and "a|b|c" in a synopsis) all come, so that none of them spells the names out by hand (only the graph usage's paragraph that describes each format names the formats itself); and the limit of seeds and tick counts (2^53 - 1). It is a header-only INTERFACE library (it links the runtime and nlohmann/json for its users), so each front end compiles it with its own settings, the extension with hidden visibility, without a second compiled target that would need position-independent code; it is neither installed nor exported. The tool's output did not change when it moved there: 38 commands gave the same standard output, standard error and exit code, byte for byte. Nor did it when the usage texts began to take their lists of names from the tables: every usage text, plain and as JSON, and every message that lists names stayed the same, byte for byte, as did the Python extension's messages.
- Service providers ([ADR-0026](ADR-0026-runtime-service-providers.md)): `RuntimeOptions::provider_paths` (searched before `PRAENORA_PROVIDER_PATH` and the installation's provider directory; declared after `module_paths` and `catalog_paths`, so positional aggregate initialization of `RuntimeOptions` changes with runtime 0.2), `ProviderInfo` and `Runtime::list_providers()`, which lists every provider manifest in search order, a shadowed one unusable, naming the manifest that shadows it (as `list_modules()` lists shadowed module manifests too); the CLI's global option `--provider-path P` and its command `providers list`. The shared front-end code adds `frontend::provider_json()`.
- Later: [ADR-0028](ADR-0028-error-records-keep-location-and-details.md) gives `ErrorRecord` the error's `location` and `details_json` (members appended), so the error that `run()` rebuilds from the run's error record, when the call that ended the run threw something other than a `praenora::Error`, has the same location and details as well.
- Later: [ADR-0042](ADR-0042-control-and-status-api-over-http.md) adds `PathForm` and `Workflow::status_json(PathForm)` (`status_json()` is the absolute form; the placeholders form is made by `Workflow::Impl::status_document()`, which the status-file writer's producer calls too, so the run's path anchors are a member of the workflow declared before the writer), and `Workflow::run_number()`, which `Runtime::open()` takes from an atomic count in the `Runtime`'s shared state once the `Workflow` exists, so an `open()` that throws takes none: the shared state is immutable but for that count. An empty `WorkflowOptions::status_file` means no status file, in place of the configuration's.

## Alternatives considered

- **Header-only runtime.** Exposes all dependencies and inflates compile times.
- **A C API for the runtime.** Stable across compilers, but more verbose; not needed while only same-toolchain consumers exist.
- **Error codes and no exceptions.** Fits the module ABI, but awkward for a rich diagnostic report.
- **Public nlohmann types.** Convenient, but couples consumers to the library version.

## Consequences

- Dependency upgrades do not break consumers' source.
- Consumers must build with the same compiler family as the shared library.
- JSON travels as strings across the public API.
