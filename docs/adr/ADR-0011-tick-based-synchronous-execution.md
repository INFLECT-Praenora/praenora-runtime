# ADR-0011: Tick-based synchronous execution; deterministic schedule; feedback by delayed connections

- Status: Proposed
- Date: 2026-11-10
- Supersedes: none
- Superseded by: none

## Context

Workflows must run deterministically and support feedback (predictions from one update inform the next estimate). Unrestricted cyclic message passing makes ordering and termination hard to define and to test.

## Decision

- Execution proceeds in numbered ticks starting at 0. Each tick runs every step once, in a schedule computed once per run: a topological order over `delay: 0` connections with ties broken by lexicographic step id.
- In tick `t`, workflow inputs produce messages first. Delay-0 inputs receive messages produced in tick `t`; delay-1 inputs receive messages from tick `t-1` and are absent at tick 0. Absent optional inputs are omitted from the invocation document.
- Feedback is a connection with `delay: 1`. `delay` is 0 or 1 in v0, and a delayed connection may only feed an optional input. The delay-0 subgraph must be acyclic (`GRAPH_CYCLE`).
- Every step runs every tick; there is no cadence or trigger mechanism (OQ-6).
- The failure policy is fail-fast: the first step failure fails the run (OQ-6).
- Termination: `run.ticks` ticks complete; or, when `run.ticks` is not set, every replay input source is exhausted; or a stop is requested; or a step fails.
- One orchestrator runs ticks and exactly one module call is in flight at a time (OQ-11).
- Outputs are validated against message-type schemas when produced; the runtime wraps them in envelopes (ADR-0020).

### Builder notes (Proposed)

- `run.ticks` is required when no replay input exists (for example when every input is a static document). Validation fails with `CONFIG_INVALID` otherwise, since the run could never terminate on its own.
- Graph validation reports every problem it finds (connections in definition order, then unconnected ports, then the first cycle), and building the graph throws the first one. The schema accepts any non-negative `delay`; a delay other than 0 or 1 is reported by graph validation as `GRAPH_INVALID`, so the message can explain the v0 rule. A delayed connection may not feed a workflow output (`GRAPH_INVALID`).
- Graph validation (`validate_graph()`, `src/runtime/graph/graph.cpp`) starts by looking up each step's capability (`CATALOG_ENTRY_NOT_FOUND`, located at `/steps/<id>/capability`). An unknown capability skips that step's connection checks: a connection that starts or ends at one of its ports is checked only for its delay value and at its other end (`PORT_UNKNOWN`, and fan-in when that end is the target), not for its message types or the placement of its delay, and the step's required inputs are not checked for connections. Of the cycles only the first one found is reported, and when there is a cycle the schedule is not computed. The schema admits any integer `delay` from 0 to 2147483647 (default 0); graph validation rejects every value above 1 as `GRAPH_INVALID` at `/connections/<i>/delay`, and such a connection takes no part in the cycle search or the schedule while the rules for delayed connections still apply to it. When a configuration is validated, the graph is validated only if every capability and message type the definition names is in the catalog (ADR-0010); `praenora graph` validates the graph of any definition.
- Cycles are searched over delay-0 connections between steps by a depth-first search that visits steps, and each step's successors, in lexicographic order; the first cycle found is reported as `a -> b -> a` (`GRAPH_CYCLE`). The schedule is Kahn's algorithm that always takes the smallest ready step id.
- The engine (`src/runtime/engine/`) starts the steps one at a time, in schedule order: load, create, initialize, then the next step. Each manifest's library is loaded once and shared by the steps that use it; once loaded, its SHA-256 is compared with the one validation computed, and a library replaced in between is refused (`LIBRARY_DIGEST_MISMATCH`, located at the manifest's `/library/path`).
- Tick `t` covers `[start + t·period, start + (t+1)·period)`, both bounds computed by multiplication. The invocation's `logical_time`, the envelopes' `logical_time` and the tick result's logical time are the window's end. Workflow inputs are read in name order, then the steps run in schedule order. A delay-1 input receives the message its producer made in the previous completed tick. A required input without a message, which a valid graph never allows, fails the run with `INPUT_MISSING`.
- A result is checked in this order: it is JSON (else `OUTPUT_INVALID` with `details.raw_prefix`, its first 200 bytes, cut back to a whole UTF-8 sequence); it satisfies `pmp-result`; it names no undeclared port (located at `/outputs/<port>`); it lacks no required output (located at `/outputs`); each output's data satisfies its message type (located at `/outputs/<port>/data<pointer>`). `details.port` names the port, and `details.issues` lists schema problems. An invalid result counts as a failed invocation. With strict validation, the envelope built around each output must then satisfy `pmp-envelope`. Only a defect of the runtime can break an envelope the engine built, so a violation is `INTERNAL` (exit 70), located at `/outputs/<port>`, with `details.step`, `details.module`, `details.port`, `details.tick` and `details.issues`; the module is not at fault, and its invocation counts as succeeded.
- A step's error carries `details.step`, `details.module` (`name@version`), `details.phase` (`load`, `create`, `initialize` or `invoke`) and, during a tick, `details.tick`. `details.cause` is the module's error document; a text that is not a JSON object, or is longer than 64 KiB, becomes `{"code", "message"}`. `details.diagnostics` is added when the instance declares `features.diagnostics` and is not unresponsive; it is asked for before the teardown, and diagnostics over 64 KiB become `{"truncated": true, "bytes", "text"}` with their first 64 KiB. Create and initialize map their outcomes as invoke does (`STEP_TIMEOUT`, `MODULE_UNRESPONSIVE`, `STEP_FAILED`). A library that does not load keeps the loader's code (`LIBRARY_LOAD_FAILED`, `MODULE_IDENTITY_MISMATCH`, ...), with phase `load`. Failures outside module calls end the run the same way, with the same cleanup: output files that cannot be written (`IO_ERROR`), input data that breaks its message type (`TARGET_DATA_INVALID`), memory (`RESOURCE_EXHAUSTED`), and unexpected exceptions or a workflow input's envelope that breaks `pmp-envelope` (`INTERNAL`, with `details.input`, `details.tick` and `details.issues`; like a step output's envelope, only a runtime defect can break it).
- A run that fails always carries its error. When something other than a `praenora::Error` (out of memory, most likely) breaks off the ending itself (teardown, output files, final record), the run still ends as `failed`, and its error is the first failure: the failure it was ending with, if any; else an error met earlier in the same ending (an output file that could not be written); else `INTERNAL` ("internal error while ending the run: ...", with the exception's message when it has one). The run records the very error that the control call that ended the run (`start()` or `run_tick()`) throws, so the two cannot disagree; `shutdown()` and the destructor only record it. The engine then makes a last attempt to update the metrics, the status and the final run record.
- With validation `off` (`EngineSettings::validate_payloads` false), input and output data are not checked against their message types, nor envelopes against `pmp-envelope`. The structure of results (`pmp-result`) and their ports are always checked, because routing depends on them.
- Validation `off` is reachable only through the engine's internal settings (`EngineSettings::validate_payloads`, in the runtime's object library): the performance probe `praenora_perf` (`tests/perf`) and white-box tests (`tests/contract/engine_test.cpp`) turn it off; no configuration key, public API or CLI option does. The probe runs the test workflow `test.noop-chain` (four `test.echo` steps in a chain, without workflow inputs, each bound to the fixture module `fx-noop`) for `--ticks N` ticks with `--validation strict` or `off`, and prints `{"ticks","steps","invocations","total_ns","mean_invocation_overhead_ns","mean_tick_ns","validation"}`. `total_ns` sums the engine's own measurement of each tick (the metrics' last tick duration, read after each tick), so neither the start of the run nor its end, which follows the last tick, counts; `invocations` is the metrics' count; `mean_invocation_overhead_ns` is `total_ns / invocations`, the runtime's cost per invocation of a module that does nothing; `mean_tick_ns` is `total_ns / ticks`. The probe fails (exit 1) unless the run completed, every step ran once per tick and succeeded, and the run record reports the validation used. CTest runs it for 2000 ticks with each setting (`perf.validation_strict`, `perf.validation_off`, label `perf`); they fail only when the probe fails or prints no report, never on timings.
- When the tick count is reached, or the replay inputs are exhausted after a tick, the engine tears down at once and enters `completed`, without passing through `stopping`; `stopping` is entered only while a stop or a failure tears down. Without `run.ticks`, a run whose replay inputs hold no data from `time.start` on completes in `start()` without a tick. `finished()` is true once the run is over (completed, stopped or failed) and when its ticks are complete or its inputs exhausted. A stop request alone does not make it true: the next `run_tick()` winds the run down without calling a module (or `shutdown()` does), so a loop of `run_tick()` until `finished()` ends as `stopped`.
- Stop: the engine starts no module call while the workflow's stop flag is up. `request_stop()` raises the flag and cancels the call in flight; instances also read the flag as their calls start (ADR-0012). The step or tick in progress then ends the run as `stopped`. A tick cut short does not count and records no outputs; its trace lines so far stay. A stopped run is not an error: `start()` and `run_tick()` return normally (`run_tick()` with `finished` set), and the run summary's error is `RUN_STOPPED`. `shutdown()` on a run that is ready or running ends it as `stopped` too.
- `request_stop()` reaches the call in flight through an atomic pointer to its instance. After each call the engine clears the pointer and waits for any `request_stop()` still using it (an atomic counter), so a late stop can neither cancel the next call, such as a finalize, nor touch an instance that is gone. Both steps are lock-free, so `request_stop()` stays async-signal-safe.
- Teardown finalizes every ready instance, last created first, then destroys every instance that exists, last created first, then releases the instances (joining their worker threads) and only then the libraries. A finalize that fails is logged, marks its step failed and becomes the step's last error; it does not change how the run ended.
- An unresponsive instance's call may still be running in its library. When the module allows no concurrent calls into its instances (`features.concurrency` `"module"`, the default), the teardown therefore calls no other instance of that library either. All the others, except those already destroyed or never created (still `loaded`), are left as they are from then on: not finalized (if they were not yet) and not destroyed, never freed, and kept for the rest of the process like the unresponsive one's host API. Their runtime services are withdrawn first (`ModuleInstance::withdraw_services()`), as an abandoned instance's are: `get_service()` returns NULL from then on, so a module thread that still asks for a service once the run and its service registry are gone reaches no freed memory. A warning (event `teardown.skipped`, with the instance's `state`) names each and says what was left undone: "is neither finalized nor destroyed" (ready), "is finalized but not destroyed" or "is not destroyed". Instances already destroyed, or never created, make no module call when they are released, so they are released as usual (the engine cannot tell whether a `failed` instance still exists in the module, so it keeps those). This also applies when an instance becomes unresponsive during the teardown itself, in its finalize or its destroy. With `"instance"`, the other instances are finalized and destroyed as usual.

## Alternatives considered

- **Asynchronous, event-driven messaging.** Natural for streaming, but ordering is hard to make deterministic.
- **Fixed-point iteration for cycles.** Can converge, but needs convergence criteria and makes results harder to reproduce.
- **Parallel execution of independent steps.** Deferred (OQ-11); sequential order keeps results independent of scheduling.
- **Delays greater than 1 or initial values for feedback.** Deferred (OQ-6).

## Consequences

- Runs are repeatable and the schedule is easy to inspect (`praenora graph`).
- Slow steps delay every later step in the tick.
- Cadence, retries and degraded modes need later design work.
